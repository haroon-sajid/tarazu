# API Contracts

This file is the single source of truth for (a) the public HTTP API between
`frontend/` and `backend/`, and (b) the internal module interfaces (`service.py`
signatures and `app/shared/` schemas). **Any contract change must update this
file and `backend/app/shared/` in the same commit**, and be announced to the
team — the frontend builds against these shapes.

The shapes below are generated by, and validated against, the Pydantic models in
[`backend/app/shared/schemas.py`](../backend/app/shared/schemas.py) and
[`backend/app/shared/api.py`](../backend/app/shared/api.py). Live OpenAPI docs
are at `http://localhost:8000/docs` once the app is running.

## Conventions

- **Every route except `/health`, `/v1/auth/signup`, and `/v1/auth/login`
  requires a credential.** Either `Authorization: Bearer <token>` (a person) or
  `X-API-Key: trz_live_...` (a machine — see "API access" below). Without one
  they return `401`. No action can reach the audit trail without an identity
  attached to it.
- **Every route is scoped to one organization, and the client never names it.**
  See "Tenancy" below. `403` means "you belong to no organization"; a resource
  in someone else's is `404`.
- All public routes are versioned (`/v1/...`) with paths in `lowercase-kebab-case`.
- Request and response bodies are JSON. Unknown keys are **rejected**, not ignored.
- Every AI-produced field carries `extraction_confidence: "high" | "medium" | "low"`
  and a `source` provenance. Every deterministic match carries
  `match_strength: "high" | "medium" | "low"`. See "Two confidences" below.
- All mutating endpoints emit an audit-trail record and return it in the response.
- Money is a JSON number. Currency is a separate ISO-4217 `currency` field
  (`"PKR"` throughout the sample data).
- Dates are `YYYY-MM-DD`. Timestamps are RFC 3339 UTC (`2026-06-19T09:41:07Z`).
- Module-to-module calls go through `service.py` only, passing `shared/` schema
  objects. Those interfaces are contracts too, and are kept microservice-extractable.

## Tenancy

**A tenant is one accounting firm — an `organization`.** Every case, document,
extraction, review item, flag, Benford result, and audit record belongs to
exactly one, and no route returns a row from any other.

How the organization is decided:

1. The bearer token identifies a **user**. It says nothing about which
   organization they are in, and any org claim inside it would be ignored.
2. The backend resolves that `user_id` to a row in `organization_members` on
   every request (`get_current_org`).
3. Every repository call underneath is filtered by that `org_id` **in the query**
   — not fetched and then checked.

**No endpoint accepts an `org_id`, in a body, a query string, or a header.** An
org id supplied by the caller would be an authorisation decision made by the
caller. `POST /v1/auth/signup` mints the id for the organization it creates; a
signup body carrying an `org_id` is rejected `422`, like any unknown key.

### `403` and `404` mean different things, deliberately

| Situation | Status | Why |
|---|---|---|
| No token, or an invalid one | `401` | Not authenticated. |
| Authenticated, but a member of no organization | `403` | About the caller, not about any row. No resource is named in the request, so nothing is disclosed. |
| A case or review item belonging to **another** organization | `404` | A `403` here would confirm the row exists — that some firm on this platform has a case `CASE-abc123`. From outside the organization, that row does not exist. |

The `404` body for another firm's case is identical to the `404` body for a case
id that was never issued to anyone, so the two cannot be told apart by response
shape, wording, or timing of the lookup. `backend/tests/test_tenancy.py` asserts
that, and `scripts/demo_tenant_isolation.py` demonstrates it end to end.

### At the database

Application-layer filtering is one of two layers, not the only one. In Postgres,
row-level security policies admit a row only when its `org_id` is in the
caller's `organization_members` — see
[`infra/supabase/0002-organizations.sql`](../infra/supabase/0002-organizations.sql).
`audit_trail` keeps its `insert` and `select` policies and gains `org_id` on
both; it acquires no `update` policy and no `delete` policy, its REVOKE stands,
and its append-only trigger is untouched.

## API access

An organization generates API keys so its own tooling — n8n, Zapier, a cron
script — can reach Tarazu without a person signing in. A key belongs to one
organization and reaches exactly what its creator could reach: the tenancy rules
above apply to it unchanged, and another firm's case is `404` to a key just as it
is to a person.

### The key

```
trz_live_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6
└──┬───┘ └────────────────┬─────────────────┘
 scheme     32 hex characters from `secrets`
└─────────┬─────────┘
   key_prefix — the non-secret head, shown in the UI and in the audit trail
```

**The key is returned once, by the call that creates it, and is never
retrievable again.** What Tarazu stores is `key_prefix` and a SHA-256 digest;
there is no code path that could show you the key a second time, because there
is nothing to show. Lose it and create a new one.

Send it as a header on any endpoint:

```
X-API-Key: trz_live_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6
```

If both `X-API-Key` and `Authorization` are present, the API key is used and the
`Authorization` header is ignored — an ambiguous request must resolve the same
way every time.

### Scopes

| Scope | Grants |
|---|---|
| `read` | `GET /v1/review-items`, `GET /v1/dashboard`, `GET /v1/review-items/{id}/audit` |
| `write` | `POST /v1/upload`, `POST /v1/review-items/{id}/approve`, `.../reject` |

Scopes are fixed for a key's lifetime: to change them, revoke and create
another. A key omitting `scopes` on creation gets `["read"]` — a key that can
approve should have to say so.

A key without the scope a route needs gets `403` (not `404`): the credential is
real and the organization is real, so there is nothing to conceal by pretending
the route does not exist.

**No key can manage keys.** `/v1/api-keys` requires a signed-in person; a key
presented there is `403`. A credential that can mint credentials would turn one
leak into permanent access and put revocation in the attacker's hands.

### What the audit trail shows

Every mutating call made with a key appends a record with:

- `actor_type: "system"`
- `actor_id: "api-key:<key_prefix>"` — for example `api-key:trz_live_a1b2c3d4`

so "which integration approved this" is always answerable, and revoking the
right key never involves guessing. The affected `review_item.decided_by` still
names the **person** who created the key: the trail records that a machine made
the call, and the record still belongs to an accountable human.

> **Worth being deliberate about.** A `write` key can approve and reject, which
> means a firm can automate the decision step. Reliability rule 1 says the human
> decides, and a key does not repeal it — it moves the human's decision from
> "clicking this item" to "authorising this workflow to click items". Tarazu
> makes that visible rather than preventing it: `read` is the default scope, the
> trail says `system`/`api-key:…` on every such row, and an auditor reviewing the
> trail can see exactly which items a person looked at and which a workflow did.
> Grant `write` when the automation is the intent, not by default.

### `POST /v1/api-keys`

Requires a signed-in person. **The only response that ever carries the raw key.**

**Request**

```json
{ "name": "n8n integration", "scopes": ["read", "write"] }
```

**Response `201`**

```json
{
  "api_key": "trz_live_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6",
  "key": {
    "key_id": "AK-e6accd1c0b16",
    "name": "n8n integration",
    "key_prefix": "trz_live_a1b2c3d4",
    "scopes": ["read", "write"],
    "created_by": "8f3a2c19-4d5e-4b7a-9c11-2e6f8a0d4b33",
    "created_at": "2026-08-22T14:33:23.787202Z",
    "last_used_at": null,
    "revoked_at": null,
    "revoked": false
  },
  "message": "Save this key now — it is shown once and cannot be retrieved again. ..."
}
```

**Errors** — `401` without a session, `403` if an API key was presented instead
of a session, `422` for an empty name, a name over 100 characters, an empty
`scopes` list, or a scope outside `read` / `write`.

### `GET /v1/api-keys`

Requires a signed-in person. Lists the organization's keys, revoked ones
included — "when did we turn that one off" is a question this screen has to be
able to answer.

**Response `200`**

```json
{
  "total": 2,
  "keys": [
    {
      "key_id": "AK-e6accd1c0b16",
      "name": "n8n integration",
      "key_prefix": "trz_live_a1b2c3d4",
      "scopes": ["read"],
      "created_by": "8f3a2c19-4d5e-4b7a-9c11-2e6f8a0d4b33",
      "created_at": "2026-08-22T14:33:23.787202Z",
      "last_used_at": "2026-08-22T14:34:02.114870Z",
      "revoked_at": null,
      "revoked": false
    }
  ]
}
```

There is no `api_key` field and no `key_hash` field on this shape, and there is
no query parameter that adds one.

### `DELETE /v1/api-keys/{key_id}`

Requires a signed-in person. Stamps `revoked_at`; the key stops working
immediately. **The row is not deleted** — the audit trail's
`api-key:<prefix>` entries stay resolvable to a name, a creator, and a date.

Revoking twice is not an error and does not move the timestamp. There is no
un-revoke: a key that was turned off may have been turned off *because it
leaked*. Create a new one.

**Response `200`** — the key's summary, now with `"revoked": true`.

**Errors** — `401` without a session, `403` if presented with an API key, `404`
for an unknown key **or one belonging to another organization**.

---

### `PATCH /v1/api-keys/{key_id}`

Requires a signed-in person. Renames the key — the one editable thing about
it. Scopes are fixed for a key's lifetime: to change what a key may do, create
a new key and delete this one.

**Request**

```json
{ "name": "n8n automation (renamed)" }
```

**Response `200`** — the key's summary with the new name.

**Errors** — `401` without a session, `403` if presented with an API key, `404`
for an unknown key **or one belonging to another organization**, `422` for an
empty name or one over 100 characters.

---

### `DELETE /v1/api-keys/{key_id}/record`

Requires a signed-in person. Permanently removes the key's row — active or
revoked. Deleting an active key stops it immediately: authentication finds
keys by hash, and the hash goes with the row.

What deletion costs is history: the audit trail's `api-key:<prefix>` entries
stay in the trail (the trail itself is append-only and untouched) but stop
resolving to a name, a creator, and a date. An organization that wants a
turned-off key to stay on the books revokes instead of deleting.

**Response `200`**

```json
{ "key_id": "AK-e6accd1c0b16", "deleted": true }
```

**Errors** — `401` without a session, `403` if presented with an API key, `404`
for an unknown key **or one belonging to another organization**.

---

### `GET /v1/profile` and `PUT /v1/profile`

Requires a signed-in person; an API key is `403` on both. The profile is
presentation only — a display name, a picture, contact details. Nothing in it
feeds authentication, tenancy, or the audit trail, which names users by id.
There is no `{user_id}` in the path: a profile is reachable only by the
person it belongs to.

**`PUT` request** — a full replacement; an omitted or blank field is cleared:

```json
{
  "full_name": "Haroon Sajid",
  "job_title": "Audit Partner",
  "phone": "+92 300 1234567",
  "avatar": "data:image/jpeg;base64,..."
}
```

`avatar` must be a `data:image/(png|jpeg|webp);base64,...` URL of at most
400,000 characters (~300 KB decoded); anything else is `422`.

**Response `200`** (both routes) — the stored profile; a person who never
saved one gets all-null fields, not a `404`:

```json
{
  "user_id": "8f3a2c19-4d5e-4b7a-9c11-2e6f8a0d4b33",
  "full_name": "Haroon Sajid",
  "job_title": "Audit Partner",
  "phone": "+92 300 1234567",
  "avatar": "data:image/jpeg;base64,..."
}
```

Backing storage: SQLite `user_profiles` (created automatically) or Supabase
`user_profiles` from `infra/supabase/0004-user-profiles.sql`.

### Trying it with curl

```bash
# 1. Sign in as a person and create the key.
TOKEN=$(curl -s -X POST http://localhost:8000/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"partner@lahore-audit.pk","password":"..."}' | jq -r .access_token)

curl -s -X POST http://localhost:8000/v1/api-keys \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"n8n integration","scopes":["read"]}'
# -> {"api_key":"trz_live_...","key":{...},"message":"Save this key now — ..."}

# 2. From then on, the machine uses only the key.
export TARAZU_API_KEY=trz_live_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6

curl -s -H "X-API-Key: $TARAZU_API_KEY" \
  'http://localhost:8000/v1/review-items?decision=pending&flagged=true'

curl -s -H "X-API-Key: $TARAZU_API_KEY" http://localhost:8000/v1/dashboard

# 3. Revoke it when the integration is retired (needs the session again).
curl -s -X DELETE http://localhost:8000/v1/api-keys/AK-e6accd1c0b16 \
  -H "Authorization: Bearer $TOKEN"
```

### Trying it with n8n

n8n needs no custom node. Use **HTTP Request** with a **Header Auth**
credential; Zapier's "API Key in header" auth and Make's "API key connection"
are configured the same way.

1. **Credentials → New → Header Auth**
   - *Name*: `Tarazu`
   - *Header Name*: `X-API-Key`
   - *Header Value*: `trz_live_...`
2. **Schedule Trigger** — every morning at 08:00.
3. **HTTP Request** node
   - *Method*: `GET`
   - *URL*: `https://your-tarazu-host/v1/review-items`
   - *Authentication*: Generic Credential Type → Header Auth → `Tarazu`
   - *Query Parameters*: `decision=pending`, `flagged=true`
4. **IF** node — `{{ $json.total }}` is greater than `0`.
5. **Slack / Email** node — post `{{ $json.total }} flagged items are waiting on
   {{ $json.case_id }}`.

A useful second workflow, for a firm that has decided to automate the
straightforward cases: filter to `match.status === "matched"` with no flags, then
`POST /v1/review-items/{{ $json.review_item_id }}/approve` with a `write` key and
a `note` saying which workflow did it. Read the note on rule 1 above before you
build that one — every such approval lands in the trail as
`api-key:<prefix>`, and it should.

**Do not** put the key in a workflow's URL, a query parameter, or a node's
plain-text field. Query strings end up in access logs and browser history; the
credential store exists so the key does not.

## Two confidences, never one

This is the contract's most important rule, and the reason there is no field
anywhere named plain `confidence`:

| Field | Where | Produced by | Means |
|---|---|---|---|
| `extraction_confidence` | `ExtractedField`, `ReviewItem` | Qwen VL | How sure the model is that it read this value correctly. |
| `match_strength` | `MatchResult` | pandas, in `matching/` | How well two rows line up. **No AI value influences this.** |

The frontend renders them as two separate columns. A test
(`test_no_schema_has_a_bare_confidence_field`) fails the build if the two are
ever collapsed into one field.

## Provenance

Every extracted value names where it came from. Two locator styles, because
Tarazu reads two kinds of source:

```jsonc
// A document (bank statement PDF, invoice PDF or photo): page + region.
{ "document_id": "DOC-BNK-001", "page": 2, "bbox": [0.605, 0.289, 0.857, 0.312],
  "text_snippet": "49,500.00", "row_number": null }

// A spreadsheet (the ledger, read by pandas with no AI involved): row number.
{ "document_id": "DOC-LED-001", "row_number": 14, "page": null, "bbox": null,
  "text_snippet": null }
```

`bbox` is `[x0, y0, x1, y1]`, normalised to 0–1 page space, origin top-left.
A page-based provenance must carry a `bbox` **or** a `text_snippet` — otherwise
the evidence viewer has nothing to highlight, and validation fails. When Qwen VL
returns unusable boxes, send `bbox: null` with a `text_snippet` and the viewer
highlights the matching text instead.

### Which case?

`/v1/review-items` and `/v1/dashboard` are always about one case. Pass
`?case_id=CASE-...`, or omit it and the backend uses **your organization's** most
recent case. With no cases in your organization, both return `404` telling you to
upload first — including when another firm's database rows are sitting right
beside yours.

### `POST /v1/auth/signup`

Creates a user, creates the organization that user's firm owns, and adds them to
it as `owner`. The three happen together: a user with no organization has
nowhere to put a case, and every other route answers them `403`.

**Request**

```json
{
  "email": "partner@lahore-audit.pk",
  "password": "at-least-8-characters",
  "organization_name": "Lahore Audit Associates"
}
```

**Response `201`**

```json
{
  "user_id": "8f3a2c19-4d5e-4b7a-9c11-2e6f8a0d4b33",
  "email": "partner@lahore-audit.pk",
  "org_id": "3c1d9e77-5b20-4a6e-8f31-9d2a7c4e1b05",
  "organization_name": "Lahore Audit Associates",
  "role": "owner"
}
```

No token comes back — sign in at `/v1/auth/login` next.

**Errors** — `409` if the email is already registered, `422` for a password
under 8 characters or for **any unknown key, `org_id` included**. There is no
way to ask to join an existing organization; inviting a colleague into yours is
a later route, and it will be authorised by your own membership.

---

### `POST /v1/auth/login`

**Request**

```json
{ "email": "partner@lahore-audit.pk", "password": "..." }
```

**Response `200`**

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 3600,
  "user_id": "8f3a2c19-4d5e-4b7a-9c11-2e6f8a0d4b33",
  "email": "partner@lahore-audit.pk"
}
```

Send `access_token` as `Authorization: Bearer <token>` on every other call.
`user_id` is what lands in `audit_trail.actor_id`.

**The token carries no `org_id` and never will.** Your organization is resolved
from your membership on each request, so a token cannot be used to act inside a
firm you have been removed from.

With Supabase configured the token comes from GoTrue, signed either with the
project's asymmetric key (ES256, the modern default, verified against the
project's published JWKS) or with the legacy HS256 shared secret. The backend
reads the algorithm from the token header and maps it to the right key, so a
project on either scheme works with no configuration change — and a token
declaring one algorithm can never be verified with the other's key material.

Without Supabase, the local SQLite store is its own identity provider and signs
the token with `LOCAL_JWT_SECRET` — same claims, same verification path — so the
whole multi-tenant flow runs with no network.

**Errors** — `401` for wrong credentials, deliberately byte-identical whether
the email exists or not.

### `POST /v1/auth/change-password`

Replaces the caller's own password. Requires a signed-in person's Bearer token;
an API key is refused with `403` — a machine credential that could rotate its
creator's password would turn one leaked key into a stolen account.

The current password must be presented and verified, so an unattended signed-in
browser is not enough to lock the owner out. Tokens already issued stay valid
until they expire: a token says who you are, and who you are has not changed.

**Request**

```json
{
  "current_password": "the-password-today",
  "new_password": "at-least-8-characters"
}
```

**Response `200`**

```json
{
  "message": "Password changed. Sessions that are already signed in stay valid until they expire; new sign-ins need the new password."
}
```

**Errors** — `400` for a wrong current password (one message, whether the
password was wrong or the account has no local password record), `400` when the
new password equals the current one, `422` for a new password under 8
characters, `401` with no token, `403` for an API key. Neither password is ever
logged or stored in clear.

### `POST /v1/upload`

Accepts the three document kinds that open a case. `multipart/form-data`.

**Request** — form fields:

| Field | Cardinality | Accepted |
|---|---|---|
| `bank_statement` | exactly 1 | `.pdf` |
| `ledger` | exactly 1 | `.xlsx`, `.xls`, `.csv` |
| `invoices` | 1 or more | `.pdf`, `.png`, `.jpg`, `.jpeg`, `.webp` |

```bash
curl -X POST http://localhost:8000/v1/upload \
  -F "bank_statement=@hbl-statement-june-2026.pdf" \
  -F "ledger=@sethi-textiles-ledger-june-2026.xlsx" \
  -F "invoices=@inv-2026-0087.pdf" \
  -F "invoices=@smw-0431-photo.jpg"
```

An optional `client_name` form field names the audited client.

This endpoint runs the whole pipeline synchronously: store the bytes, extract
with Qwen VL (or from cache when `DEMO_MODE=true`), read the ledger with pandas,
call `matching.service.run_matching`, call `rules.service.evaluate_flags`, and
save the review queue. On a real statement that takes tens of seconds; moving it
to a background job is a later change behind this same response.

**Response `201 Created`**

```json
{
  "case_id": "CASE-4f2a9c1b03",
  "documents": [
    {
      "document_id": "DOC-BNK-7a1c9e02",
      "document_type": "bank_statement",
      "filename": "hbl-statement-june-2026.pdf",
      "size_bytes": 418233,
      "storage_path": "CASE-4f2a9c1b03/DOC-BNK-7a1c9e02/hbl-statement-june-2026.pdf"
    }
  ],
  "status": "ready_for_review",
  "review_item_count": 10,
  "needs_human_review_count": 1,
  "message": "10 items are ready for review."
}
```

`status` is the case status: `uploaded`, `extracting`, `awaiting_matching`,
`ready_for_review`, or `failed`. `needs_human_review_count` is how many
documents had the two extraction passes disagree.

> **`awaiting_matching`** means extraction finished and the documents are saved,
> but `matching/` and `rules/` are not implemented yet, so there is no review
> queue. The response says so rather than inventing results. See "Internal
> module interfaces" below.

**Errors**

| Status | When |
|---|---|
| `401` | No credential, or an unknown/revoked API key |
| `403` | You belong to no organization, so there is nowhere to open the case; or the API key lacks the `write` scope |
| `413` | A file is larger than 25 MB |
| `415` | A file's extension is not accepted for its slot |
| `422` | A required slot is missing, `invoices` is empty, a file is empty, or the ledger could not be read |
| `502` | Qwen was unreachable. Set `DEMO_MODE=true` to run on cached extractions. |

### `POST /v1/review-items/{id}/reject`

Records one human rejection. **A reason is required by the contract**, not just
by the UI: rejecting without saying why would leave a hole in the audit trail.

**Request**

```json
{ "reason": "No supporting invoice provided by the client." }
```

**Response `200`** — same shape as approve, with `decision: "rejected"`,
`rejection_reason` set, and `audit_record.action: "item_rejected"`.

**Errors, both endpoints**

| Status | When |
|---|---|
| `401` | No credential — a decision cannot be recorded without an identity — or an unknown/revoked API key |
| `403` | You belong to no organization; or the API key is `read`-only and this route needs `write` |
| `404` | No review item with that id **in your organization**. Another firm's item is `404` too, and an already-decided item of theirs is still `404`, never `409`. |
| `409` | The item already carries a decision. Decisions are never silently overwritten. |
| `422` | Reject called without a non-empty `reason` |

A refused decision writes nothing: no half-decision on the item, and no audit
record. That holds for a cross-tenant attempt as well — the item is never
loaded, so nothing is written and nothing is disclosed.

### `GET /v1/dashboard`

Case summary. Every number here is **counted from deterministic results** — no
figure on this screen is produced or estimated by a model.

**Response `200`**

```json
{
  "case_id": "CASE-2026-06-STX",
  "client_name": "Haroon Textiles",
  "period_start": "2026-06-01",
  "period_end": "2026-06-30",
  "total_review_items": 10,
  "match_status":          { "matched": 8, "partial": 1, "unmatched": 1 },
  "decisions":             { "pending": 8, "approved": 1, "rejected": 1 },
  "extraction_confidence": { "high": 8, "medium": 1, "low": 1 },
  "flagged_item_count": 5,
  "total_flags": 8,
  "flags_by_severity":     { "high": 6, "medium": 1, "low": 1 },
  "benford": {
    "sample_size": 10,
    "digits": [
      { "digit": 1, "observed_count": 2, "observed_frequency": 0.2,
        "expected_frequency": 0.301, "deviation": -0.101 }
    ],
    "chi_square": 12.21,
    "degrees_of_freedom": 8,
    "deviates_significantly": false
  },
  "audit_readiness_score": {
    "score": 60,
    "matched":        { "percent": 80.0, "count": 8,  "total": 10 },
    "flags_reviewed": { "percent": 0.0,  "count": 0,  "total": 8  },
    "completeness":   { "percent": 100.0,"count": 10, "total": 10 }
  },
  "data_confidence": "Based on 1 month of data, 1 unmatched item and 1 partial match remain.",
  "next_best_actions": [
    {
      "action": "Check the duplicate payment to Karachi Packaging Co.",
      "severity": "high",
      "rule_id": "duplicate-invoice",
      "review_item_id": "RI-0002",
      "party_name": "Karachi Packaging Co."
    }
  ],
  "estimated_hours_saved": 0.7
}
```

`benford.digits` always has exactly nine entries, digits 1 through 9 in order.

The three breakdowns each sum to `total_review_items`, and `flags_by_severity`
sums to `total_flags`. That is enforced by the schema and asserted across
fixtures by `test_dashboard_counts_match_the_review_queue`.

#### `audit_readiness_score`

A score out of 100, plus the three components it came from, so the UI can show a
breakdown and the auditor can see what is dragging. Each component reports its
own counts, so "80%" can be shown as "8 of 10 matched" rather than a bare number
nobody can check.

| Component | Counts |
|---|---|
| `matched` | Ledger rows with a confirmed counterpart, over all rows. **A `partial` match does not count** — an amount that disagrees with the bank is not reconciled. |
| `flags_reviewed` | Flags sitting on an item a human has decided, over all flags. **A case with no flags scores 100**: there is nothing outstanding. |
| `completeness` | Rows with no blank ledger field *and* no unreadable extraction behind them, over all rows. |

`score` is the equal-weighted mean of the three percentages, rounded. The
weighting is a named constant (`READINESS_WEIGHTS`) rather than an inline
expression, so it can be argued about in review.

Every figure is counted from persisted deterministic results. Changing an
extraction confidence moves none of them, which
`test_no_metric_depends_on_an_ai_output` asserts.

#### `data_confidence`

One computed sentence, built from real counts. It states what is present and
what is outstanding, and deliberately never characterises the data as reliable
or unreliable — the auditor draws that conclusion.

```
"Based on 1 month of data, 3 unmatched items remain."
"Based on 2 weeks of data, every ledger row has supporting evidence."
"No data yet. Upload a bank statement, invoices, and a ledger to begin."
```

The period is described in the unit a person would use — days under 11, weeks
under 25, months beyond — and singular and plural forms are handled.

#### `next_best_actions`

Outstanding flags reworded as work, most severe first, at most five. Each links
back to its item so the UI can make it clickable.

Three behaviours worth knowing:

- **Decided items are excluded.** An action telling an auditor to review
  something they already approved is noise, not a queue. Approving an item
  removes its actions from the next response.
- **Flags spanning rows are collapsed.** Structuring and duplicate-payment rules
  fire once per row involved, so one issue would otherwise eat two of the five
  slots. Flags naming the same rule and the same set of rows count as one.
- **Ties break on amount, largest first.** Among equally severe flags, the bigger
  number is the one to look at first.

Wording comes from a per-rule template, with a readable fallback for rules the
dashboard has not met — `rules/` is owned separately and will grow rules this
layer has not heard of, and an unknown rule must degrade rather than disappear.

## Internal module interfaces

Modules talk only through `service.py`, passing `app/shared/` schema objects.

```python
# app/modules/matching/service.py   — owned by Dev-D. Never imports an AI client.
def run_matching(
    ledger: list[LedgerEntry],
    bank: list[BankTransaction],
    invoices: list[Invoice],
) -> list[MatchResult]: ...

# app/modules/rules/service.py      — owned by Dev-D. Never imports an AI client.
def evaluate_flags(
    ledger: list[LedgerEntry],
    matches: list[MatchResult],
    config: dict[str, Any],
) -> list[Flag]: ...
```

Both are pure functions: DataFrames and schema objects in, schema objects out.
No FastAPI, no Supabase, no file I/O, no network. The same inputs always produce
the same outputs, which is what makes the test suite meaningful evidence that
the matching is deterministic.

**Neither is implemented yet.** `app/pipeline.py` calls them for real. When they
raise `NotImplementedError` the case is parked at `awaiting_matching` with its
documents and extractions saved, and `POST /v1/upload` says so. The moment those
two functions land, the same code path completes with no change to the pipeline.

#### Benford, and the one interface still to be agreed

`GET /v1/dashboard` returns the Benford first-digit distribution so the frontend
can chart it. First-digit analysis is deterministic arithmetic over ledger
amounts, so it belongs in `rules/` beside every other deterministic test — not
in the app layer, and not duplicated.

The pipeline calls it through an optional interface: if `rules.service` exposes
`benford_analysis`, the result is computed and stored per case. Until it does,
the dashboard reports `"benford": null` rather than computing it elsewhere.

```python
# app/modules/rules/service.py — to be added by its owner
def benford_analysis(ledger: list[LedgerEntry]) -> BenfordResult: ...
```

`BenfordResult` carries `sample_size`, `chi_square`, `degrees_of_freedom`,
`deviates_significantly`, and nine `digits` entries — each with
`observed_count`, `observed_frequency`, `expected_frequency`, and `deviation`.

#### extraction

```python
# app/modules/extraction/service.py
def extract_document(document_id, document_type, filename, content) -> ExtractionResult
def read_ledger(document_id, filename, content)                     -> list[LedgerEntry]
def invoices_from(result: ExtractionResult)                         -> list[Invoice]
def bank_transactions_from(result: ExtractionResult)                -> list[BankTransaction]
```

The last two turn readings into the typed rows `run_matching` takes. They live
in `extraction/` because that is the only module that knows how a reading maps
onto a column; they perform no arithmetic.

`assistant/` and `reports/` interfaces are defined as those modules land.
